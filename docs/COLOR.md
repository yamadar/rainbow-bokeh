# 美しい配色の知識 — 理論とプログラム化

人間が「美しい」と感じる色の組み合わせを調査し、本プロジェクト（`rainbow-bokeh`）で
配色をコードから生成・操作するための指針としてまとめたもの。

現状のコードは粒子・オーラ・波紋をすべて単一色相 `BULB_HUE = 34`（暖色アンバー）の
`hsla()` で描画している（`src/config.js` / `src/render.js`）。背景のみ `src/style.css` に
固定の虹色グラデーションを持つ。本ドキュメントは、この配色を「理論的根拠を持って」
プログラム生成へ拡張するための土台。

---

## 1. なぜ人は配色を「美しい」と感じるのか

配色の好みは **生物進化 + 文化的学習 + 色同士の相互作用** の合成で説明される
（研究知見の要約）。

- **進化的基盤**: ヒトの三色型色覚は、緑の葉に対する赤い果実など「健康・生存に
  有利な対象」を見分けるよう調整されてきた。鮮やかな暖色と寒色の対比に対する
  本能的な選好はここに由来する。
- **自然さ (naturalness)**: 自然の光景に現れる色構成（空〜地平〜植生のような
  明度勾配と限定的な色相幅）に近い配色ほど美しいと評価される傾向。「色を自然に
  使う普遍的テンプレート」が部分的に生得的に存在するという仮説。
- **色対の相互作用**: 単色の好みより「2色以上の組み合わせ」での評価が支配的。
  研究上、次の2軸が分離される。
  - **preference（好ましさ）** — 構成色そのものの好み + **明度コントラスト**に強く依存。
  - **harmony（調和）** — **色相の近さ**に強く依存（似た色相ほど調和的）。
  - つまり「調和的＝似た色相」「ダイナミック＝明度差」。両者は別物で、優れた
    配色は **色相を絞りつつ明度差をつける**ことで両立する。
- **学習による分岐**: 訓練を受けていない人は高彩度を好み、訓練された作り手は
  低彩度・複雑な配色を好む。汎用 UI は前者寄り、作品性を出すなら後者寄り。

実務的な結論: **「色相は狭く、明度・彩度に構造を持たせる」** 配色が安全に美しい。
虹のように全色相を使う場合も、明度カーブとリズムで秩序を与えると破綻しにくい。

## 2. 古典的な配色理論（色相環ベース）

色相環（HSL/HSV の hue, 0–360°）上の角度関係で配色を分類する伝統的手法。
基準色相 `h` から関係色相を機械的に算出できる＝**そのままプログラム化可能**。

| 調和タイプ                 | 色相の取り方                | 性格                       |
| -------------------------- | --------------------------- | -------------------------- |
| モノクロマティック         | `h` 固定、明度/彩度のみ変化 | 最も安全。統一感が高い     |
| アナロガス（類似）         | `h`, `h±30°` 程度           | 自然で穏やか。自然界に多い |
| コンプリメンタリ（補色）   | `h`, `h+180°`               | 強い対比。鮮烈だが扱い注意 |
| スプリットコンプリメンタリ | `h`, `h+150°`, `h+210°`     | 補色より緊張を緩和         |
| トライアド                 | `h`, `h+120°`, `h+240°`     | 均等で活発。バランス良     |
| テトラード / スクエア      | `h+90°` ずつ4色             | 情報量が多く制御が難しい   |

注意点（古典理論の弱点）:

- 色相環が **RGB/HSL ベースだと知覚的に等間隔でない**。HSL で `h` を等間隔に
  回しても、人の目には黄が明るく青が暗く見え、明るさがバラつく。
- 補色を RGB/HSL で線形補間すると中間がくすんだ茶/灰になりやすい。
- → 古典理論は「関係の決め方」としては有効だが、**実際の色生成は知覚均等な
  色空間で行うべき**（次節）。

---

## 3. 知覚均等色空間 — プログラム化の鍵（OKLCH / OKLab）

`OKLab`（Björn Ottosson, 2020）とその円筒表現 `OKLCH` は **知覚的に均等**な色空間。
パレットをコードで操作する現代的な基盤。

- 成分: **L**（明度 0–1）, **C**（彩度/chroma）, **H**（色相 0–360°）。
- HSL との決定的な差:
  - L を固定して H だけ回すと、**どの色相でも知覚上の明るさが揃う**
    （HSL では揃わない）。
  - 2色を OKLCH で補間するとグラデーションの中間が **濁らず鮮やか**に保たれる。
    補色グラデーションの「茶色い中間点」問題が起きない。
  - 色相・彩度のドリフトがない（明度を変えても色相が狂わない）。
- CSS は `oklch(L C H / alpha)` を直接サポート（モダンブラウザ）。Canvas の
  `fillStyle` でも文字列として利用可能。
- 「muddy zone（くすむ色域）」— 暗い黄〜茶などは知覚的に汚く見えやすい。
  良質なライブラリ（後述）はこの帯域を**避けるように色相を曲げる**。

実務指針: **配色の「関係」は色相環（第2節）で決め、「具体的な色値」は OKLCH で
生成・補間する。** これが古典理論と現代手法の正しい組み合わせ方。

---

## 4. プログラム化できるアルゴリズム

配色生成は十分にアルゴリズム化できる。代表的な手法:

### 4.1 ハーモニー＋明度ランプ

1. 基準色相 `h` を選ぶ（時間・乱数・ポインタ位置などで駆動可）。
2. 第2節の調和タイプで関係色相 `[h, h+k, ...]` を算出。
3. 各色相に対し **明度ランプ**（例 L: 0.30 → 0.95 を数段）を掛け、
   彩度は「明るすぎ／暗すぎる端で chroma を落とす」山なりカーブにする。
   → 明度差（preference）と色相の秩序（harmony）を両立。

### 4.2 Hue cycling + イージング（`rampensau` 系の考え方）

色相を一定方向に回しながら、明度・彩度をイージング関数で変調する。
少数の数値パラメータだけで多彩で統一感のあるランプが出る。本プロジェクトの
ような「連続的に揺らぐ多数の粒子」と相性が良い。

### 4.3 ΔE による距離制御

`OKLab` 上の2点間ユークリッド距離 ≒ 知覚差（ΔE）。

- 「区別できる N 色」を作る → 距離を一定以上に保ってサンプリング。
- 「滑らかなグラデーション」→ 距離を等間隔に刻む。

### 4.4 既存ライブラリ（参考・実装の裏取り）

- `evilmartians/harmony` — OKLCH + APCA で彩度・コントラストを揃えた UI パレット。
- `meodai/rampensau` — hue cycling + イージングのパレット生成関数。
- `meodai/pro-color-harmonies` — OKLCH ベース。muddy zone を避ける後処理付き。
- `apcach` — OKLCH で hue/chroma/lightness を contrast 目標から逆算。

## 5. rainbow-bokeh への適用（実装済み）

下記5案は実装済みで、画面上部のトグルパネル（`index.html` の `#panel`）から
**実行時に個別 ON/OFF** できる。フラグの既定値は `config.js` の `COLOR_FLAGS`、
配色ロジックは純粋モジュール `color.js`、毎フレーム `render.js` へ
`colorCtx = { flags, hue }` で渡る。

| パネル表示 | フラグ          | 対応案                           |
| ---------- | --------------- | -------------------------------- |
| 色相幅     | `hueSpread`     | 案1: 粒子ごとのアナロガス色相幅  |
| 明度ランプ | `lightnessRamp` | 案2: サイズ相関の明度ランプ      |
| OKLCH      | `oklch`         | 案3: グラデーションを OKLCH 出力 |
| 背景調和   | `bgHarmony`     | 案4: 色相幅圧縮＋明度持ち上げ    |
| 色相回転   | `hueDrift`      | 案5: 基準色相の緩やかな周回      |

各案の設計意図と実装:

- **案1 粒子に色相の幅を持たせる**: 単一値 `BULB_HUE` ではなく、基準色相
  ±`HUE_SPREAD_DEG`（26°）のアナロガス範囲を粒子ごとに割り当てる（第2節
  「アナロガス」＝自然で穏やか）。粒子は生成時に `hueSeed`（[-1,1) の係数）を
  保持し、`color.js` の `particleHue()` が基準色相と合成する。
- **案2 明度に構造を**: 粒子の `sizeU`（サイズ乱数）と相関させ「大きい粒＝
  暗く落ち着く／小さい粒＝明るく弾ける」明度ランプ（`LIGHT_RAMP_MIN..MAX`）を
  `particleLightness()` で算出。preference を支える明度コントラストが得られる。
  ランプ OFF 時は従来の `p.lightness`（ランダム）にフォールバック。
- **案3 OKLCH 出力**: グラデーションストップを `hsla` から `oklch()` へ。
  `color.js` の `hslToOklch()`（sRGB→OKLab 変換, Ottosson）で同等色へ変換し、
  `colorStop()` が出力色空間を切替える。知覚均等なため遷移の濁りが減る。
- **案4 背景との調和**: 背景（`style.css`）は全色相の虹。粒子は `mix-blend-mode:
plus-lighter` で加算合成されるため、色相幅を `BG_HARMONY_HUE_FACTOR` で圧縮し
  明度を `BG_HARMONY_LIGHT_BOOST` 持ち上げると、背景の色を拾って美しく光る。
- **案5 時間変化**: 基準色相を `HUE_DRIFT_SPEED` で緩やかに周回。`main.js` が
  累積回転量 `driftHue` を持ち、フラグ ON のフレームのみ進めるのでトグル時に
  色が跳ばない。背景の `hueCycle` より十分遅くするとリズムが生まれる。

実装方針（`CLAUDE.md` の規約準拠）: 色相「関係」は第2節、具体値の生成・補間は
第3節（OKLCH）で行う。純粋な配色ロジックは `color.js` に集約し Vitest で検証
（`color.test.js`）。色文字列の組み立て呼び出しは `render.js` 側、フラグの実行時
切替（トグルパネル配線）は薄いエントリ `main.js` 側に置く。
